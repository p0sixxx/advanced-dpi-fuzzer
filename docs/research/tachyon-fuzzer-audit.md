## 1. Как устроен встроенный подборщик

Конвейер `L/diagnostics/fuzzer.uc` → `run_fuzzer_worker()`:

1. `detect_dpi_type()` — прогон целей без обхода, отбрасывание целей с недоступным L4.
2. `get_strategies_for_engine(engine, mode, target)` — **фиксированный список** стратегий
   (`presets` / `combinatorial` / `adaptive` / `custom`), `L/diagnostics/fuzzer/strategies.uc`.
3. Stage 1 «Exploration»: **по одному** прогону каждой стратегии (`fuzzer.uc:330-435`).
4. Stage 2 «Verification»: только 3–5 лучших по score Stage 1 получают **3 повтора**
   (`fuzzer.uc:444`, `fuzzer.uc:476`).
5. Бейджи и запись лучшего результата в `/etc/tachyon/fuzzer_history.json`.

Проба (`L/diagnostics/fuzzer/probe.uc`) для движка `desync` поднимает временный
`tachyon-core run -c` с `mixed`-инбаундом `127.0.0.1:11090` и единственным `desync`
аутбаундом, затем `curl -x socks5h://…` по каждой цели (`probe.uc:336-470`), а через nft
помечает исходящий трафик роутера меткой `0x08000000`, чтобы его не перехватил TProxy.

Сильные стороны, которые мы сохраняем: отделение L4-блокировки от DPI по baseline,
проверка обрыва 16 КБ, проверка сертификата (`curl exit 60`), отказ засчитывать UDP-стратегию,
если проба не отправила UDP (`probe.uc:udp_probe_verdict`).

## 2. Найденные недостатки (с доказательствами)

### 2.1. Пространство поиска Native Desync неполное и частично недостижимое

* **Fooling не перебирается вообще.** `generate_combinatorial_desync()`
  (`strategies.uc:1645-1717`) формирует `mode × split_pos × ttl × fake_sni` и
  ни разу не задаёт `fooling`. `repeats` зафиксирован на 6, `split_delay_ms` — 0 или 2.
* **Валидатор подборщика отвергает половину параметров интерфейса.**
  `parse_desync_outbound()` (`L/diagnostics/fuzzer_runner.uc:153-258`):
  * `split_pos` принимает только `midsld|sld|host|sni|sniext|<число>` (строка 185+).
    Значения из UI `sniext+1`, `host+1`, `midsld-2`, `midsld+2`, `endhost-1`, `extlen` и
    списки `1,midsld`, `1,sniext+1,midsld` возвращают `null` → стратегия отбрасывается.
  * `DESYNC_FOOLING` (строка 90) = `md5, autottl, timestamp, ts, badseq, badsum`.
    Пункты UI `md5_badack`, `badack`, `datanoack`, `badseq_badack_badsum`, `hopbyhop`
    подборщиком **не могут быть проверены**.
  * Нет ключей `seqovl`, `syndata`, `wsize`, `ipfrag`, `udplen`, `tlsrec_first`, которые
    понимает транслятор UCI (`L/config/connections.uc:1700-1712`) и которые описаны
    в CHANGELOG tachyon-core 0.3.0.
  * `multi_disorder` отсутствует в `DESYNC_PRESETS`, а `mode=multidisorder`
    нормализуется в `fake_disorder` (`fuzzer_runner.uc:133-151`), т. е. подборщик тестирует
    не тот режим, который потом применяется (`connections.uc` маппит его в `multi_disorder`).
  * `sld` и `host` молча превращаются в `midsld` (семантика zapret: `host` — начало имени,
    `sld` — начало домена второго уровня, а не середина).
* Режим `adaptive` для `desync` возвращает те же 20 ручных записей `STRATEGIES_DESYNC`
  (`strategies.uc:1915-1933`) — адаптации параметров нет.

### 2.2. Стратегии других движков генерируются с ошибками синтаксиса

* **zapret2 (nfqws2): `fooling=` — пустая операция.** В nfqws2 fooling задаётся прямыми
  аргументами функции (`:tcp_md5`, `:badsum`, `:tcp_seq=…`): `apply_fooling()` читает
  `desync.arg.tcp_seq`, `desync.arg.tcp_md5` и т. д. (`zapret2/lua/zapret-lib.lua:928-1040`,
  `desync_opts()` строки 421-430). Аргумент `fooling=badsum` создаёт `arg.fooling`, который
  никто не читает. Затронуты `strategies.uc:1339,1358,1413,1417,1868` и пресеты
  `share/tachyon/dpi-presets.json` (`z2r_rkn_fake_multidisorder`, `z2r_rkn_fake_ts_badsum`,
  `z2r_hostfakesplit_*`, `z2r_badseq_increment_*`, `z2r_fake_split2_google_blob`) — фейки уходят
  **без fooling**.
* **zapret v1 (nfqws): `--dpi-desync-fooling=badack` недопустим.** `parse_fooling()`
  (`zapret/nfq/nfqws.c:1265-1291`) знает только `none md5sig ts badsum badseq datanoack
  hopbyhop hopbyhop2`; `DEFAULT_PATTERNS.zapret.foolings` (`strategies.uc:51`) и генератор
  (`strategies.uc:1488-1540`) используют `badack`. Пресет `z1r_hostfakesplit_rzd_v1` содержит
  `--dpi-desync-fooling=badsum,tcp_seq=1000000` — синтаксис nfqws2 в nfqws1.
* **ByeDPI: `--auto=t,r,a,s` недопустим** (`byedpi/main.c:905-935` принимает `t r s c n p=`),
  `-s midsld` недопустим (`parse_offset()` `main.c:570-620` принимает только
  `offset[:r:s][+s|h|n[e|m|r|s]]`). Затронуты `strategies.uc:60,1583,1588,1893,1898,1906`.
* Валидаторы Tachyon (`L/providers/*/validator.uc`) проверяют только **имена** флагов, но не
  значения, поэтому такие стратегии доходят до пробы, демон не стартует или работает
  не так, как задумано, и стратегия записывается в «не работает».

### 2.3. Статистика и оценка

* Stage 1 — **один** прогон; отбор в Stage 2 по одному наблюдению. Нестабильная стратегия,
  случайно прошедшая один раз, вытесняет стабильную, случайно упавшую.
* Stage 2 — всего 3 повтора, `stability_pct` ∈ {0, 33, 66, 100}. При 3/3 нижняя граница
  95 % доверительного интервала Уилсона для успеха ≈ 0.44 — «100 %» статистически не значит
  «стабильно».
* Score (`fuzzer.uc:517`) — линейная смесь «стабильность×4 + латентность + скорость» без
  учёта числа наблюдений; доменные результаты сворачиваются в одну оценку, отдельная
  статистика по целям не хранится.
* `consecutive_plateau >= 8` (`fuzzer.uc:431`) прерывает adaptive-прогон после 8 стратегий
  без улучшения score — при шумном score это прерывание по случайности.
* Успехом считается любой HTTP 401/403/404/405/421 (`probe.uc:242`). Это корректно как
  признак «TLS прошёл», но проверки содержимого нет; страницы < 16 КБ не позволяют
  выявить обрыв потока ТСПУ на 16–20 КБ (проверка `probe.uc:191` срабатывает только если
  сервер отдал ≥ 10 КБ).
* Нет контрольного (заведомо доступного) ресурса между пробами: кратковременный обрыв
  канала помечает подряд идущие стратегии как неработающие.
* Нет проверки разных IP CDN и раздельных IPv4/IPv6 прогонов.

### 2.4. Обучение

* «История» — только `best_strategy` последних прогонов, подмешиваемый как «⭐ Prior Winner»
  (`strategies.uc:1832-1843`). Неудачи, статистика параметров, устаревание и детект
  изменения поведения сети отсутствуют.

### 2.5. Применение стратегии (важно для пользователя)

* В `connections.uc:1678` и `1734`: строка `desync_opts` («Строка стратегии
  десинхронизации (Fuzzer / CLI)») **читается только при пресете `custom` или пустом**.
  При выбранном Adaptive 2.0 значение `mode=fake_split split_pos=1 fake_ttl=6 …`
  игнорируется. На скриншотах пользователя именно такая комбинация.
* При пресете `auto` (Adaptive 2.0) tachyon-core сам переключает стратегии; измерение
  «стратегии» с включённым `auto_tune` измеряет адаптивный движок, а не стратегию.
  Наш фаззер всегда задаёт режим явно и выключает `auto_tune` при измерениях.

### 2.6. Расхождение исходников tachyon-core и бинарника

Публичный `crates/core-runtime/src/outbound/desync/config.rs` поддерживает только
`fake_split|split|disorder|tlsrec|fake|oob|auto`, `split_pos ∈ {число, sni, midsld}`
и вообще не знает `fooling`/`auto_tune`. CHANGELOG 0.2.2–0.3.0 описывает Adaptive 2.0,
`MultiDisorder`, `BadAck`, `HopByHop`, `seqovl`, `ipfrag`, `syndata`, `wsize`, `rndsni`,
`udplen`, массивы `split_pos`. Значит, публичный код — старый снимок, а реальные
возможности определяются только бинарником. Поэтому Advanced DPI Fuzzer **определяет
возможности установленного бинарника эмпирически** (`adf-agent caps`, см.
`docs/openwrt-agent.md`) и не генерирует параметры, которые бинарник отвергает.
Ограничение: ключ, который бинарник молча игнорирует, через `check` не обнаружить —
такие ключи выявляются на этапе упрощения (удаление параметра не меняет результат).

### 2.7. Избыточные кандидаты

`generate_combinatorial_desync()` перебирает `fake_ttl × fake_sni` и для `disorder`, хотя
`DesyncMode::Disorder` в tachyon-core отправляет первый сегмент с TTL=1 и не использует
`fake_ttl`/`fake_sni`/`repeats` (`crates/core-runtime/src/outbound/desync/engine.rs`), а для `fake`
перебирает `split_pos`, который этим режимом не используется. Из 282 кандидатов combinatorial-режима
уникальных после канонизации **138** — около половины проб повторяют эквивалентные конфигурации
(проверяется тестом `test_tachyon_v2_emulation_has_redundant_candidates`).

### 2.8. Применение найденной стратегии

`apply_strategy()` (`L/diagnostics/fuzzer.uc:786-860`) записывает только те опции, которые есть в
строке стратегии. Ранее заданные `desync_fooling`, `desync_auto_tune` и прочие остаются, поэтому
применённая конфигурация может отличаться от измеренной (например, `auto_tune=1` позволит ядру
переключиться на другую стратегию). ADF при экспорте задаёт все опции явно и удаляет лишние.

### 2.9. Наблюдения на роутере пользователя

GL.iNet Flint 2, OpenWrt 25.12.6 (`mediatek/filogic`, aarch64_cortex-a53), tachyon-core 0.3.4,
curl 8.23.0/mbedTLS **без HTTP/3** (QUIC/UDP-стратегии на роутере измерить нельзя). Разбор
`/etc/tachyon/fuzzer_history.json` (15 прогонов, `adf tachyon-history`):

* Тип блокировки везде одинаков: TCP устанавливается, TLS-рукопожатие зависает — ClientHello
  отбрасывается по SNI. При этом в 14 прогонах `dpi_detection.details` пишет «TCP connect timed
  out», что противоречит собственным метрикам пробы (`TLS handshake stalled after TCP connect`).
* Работают почти только `fake_split` с низким TTL (из пресетов — 1–3 из 18; в combinatorial — 17–20
  из 276). Одна и та же стратегия `fake_split pos=1 ttl=4 sberbank.ru` побеждала 5 раз со
  стабильностью 66 %, 66 %, 33 %, 100 %, 100 %; у YouTube за 4 дня было 4 разных «лучших».
  Это ровно эффект оценки по 1 + 3 пробам.
* TTL 6 стабильнее TTL 4 — вероятно, DPI находится примерно в 5 хопах и фейки с TTL 4 иногда до
  него не доходят. Методы, не зависящие от TTL (`md5`, `badseq`, `badack`, `datanoack`), а также
  `fake_disorder`/`multi_*` и позиции `host+1`/`sniext+1` подборщиком ни разу не проверялись.
* Прогон на незаблокированной цели (`custom`, «no DPI blocking detected») всё равно выдал
  «лучшую» стратегию `preset=oob`.
* Имена победителей разрастаются: `⭐ Prior Winner: ⭐ ⭐ Prior Winner: …`.
* Суммарно ~70 минут подбора, из них 3 combinatorial-прогона по ~18 минут.

Текущая конфигурация (`adf import`): `YouTube_desync` — `preset=auto` плюс явные
`split_pos=1 fake_ttl=6 fake_sni=max.ru repeats=6 fooling=autottl` (передаются ядру вместе с
пресетом, а `desync_opts` игнорируется); `Discord_desync` и `src_zapret2_YouTube_API` —
фиксированные `fake_split`. Неуказанные опции (`split_delay_ms`, `udp_fake`) получают значения
по умолчанию ядра, а не «выключено».

Уточнение после первых реальных прогонов: секция с `action=desync` строит аутбаунд из своих
`desync_*`, а источник из `outbound_source_refs` не влияет на него, даже если задаёт опции, которых
в секции нет (сверено с `/etc/tachyon-core/config.json`). Поэтому `src_zapret2_YouTube_API` выше не
был рабочей конфигурацией. Источники работают для секций других типов, групп и балансировщиков.

### 2.10. Что изменилось в подборщике Tachyon 1.7.12

Генератор запущен на роутере для движка `desync` (`fuzzer.uc generate desync <режим>`):

| Режим | Кандидатов | Различаются по поведению на TCP |
|---|---:|---:|
| `presets` | 22 | 22 |
| `adaptive` | 24 | 24 |
| `combinatorial` | 519 | около 140 |

До версии 1.7.12 было 282 кандидата и 138 различающихся, поэтому рост в основном дали копии с `udp_fake`
(244 кандидата). `fake_disorder`, `multi_split` и `multi_disorder` не генерируются, `fooling` не
перебирается, `repeats` почти всегда равен 6, а позиций по-прежнему четыре: `1`, `2`, `midsld`, `sni`.
Валидатор теперь принимает `seqovl`, `wsize`, `ipfrag`, `tlsrec_first`, но генератор их не использует,
а `syndata` есть только в одной стратегии. `host+1` валидатор всё ещё отвергает, поэтому стратегии с ним
нельзя проверить в этом подборщике даже вручную. Оценка осталась прежней: одна проба на кандидата и три
повтора для пяти лучших.

### 2.11. Обновление ядра и большое приветствие

Замеры на Flint 2 от 4 и 5 ноября 2026 года, `compare`, 30 кругов, `fake_disorder split_pos=host+1`:

| Ядро | `youtube-www` | `youtube-video` | `youtube-img` |
|---|---:|---:|---:|
| 0.3.4 | 59/60 | 29/30 | 60/60 |
| 0.3.6 | 0/60 | 0/30 | 60/60 |
| 0.3.4 после отката | 60/60 | 30/30 | 60/60 |
| 0.3.7 | 0/56 | 0/24 | 48/48 |

Конфиг не менялся. С Tachyon 1.7.13 на ядре 0.3.7 YouTube не работал, на ядре 0.3.4 заработал, так что
поломка следует за ядром. Какое изменение её вызвало, неизвестно: исходников ядра в репозитории нет.

После отката YouTube всё равно зависал в Chrome на всех устройствах, хотя все пробы `curl` проходили.
Проверка OpenSSL показала причину: приветствие 1415 байт в одном сегменте проходит, а 2670 байт в двух
сегментах нет. Чтобы увидеть это, приветствие должно прийти к движку частями: на loopback оно доходит
целиком и завышает результат. Замеры через LAN, ядро 0.3.4, большое приветствие на `www` и `googlevideo`:

| Стратегия | `www` | `googlevideo` | маленькое, 6 попыток |
|---|---:|---:|---:|
| `multi_disorder split_pos=1,sniext+1,midsld fake_ttl=10 repeats=4` | 10/10 | 10/10 | 6/6 |
| `fake_disorder split_pos=1 fake_ttl=10 repeats=4 tlsrec_first=1` | 9/10 | 10/10 | 6/6 |
| `tlsrec split_pos=midsld` | 10/10 | 10/10 | 0/6 |
| `fake_disorder split_pos=1 fake_ttl=10 repeats=4` | 8/10 | 6/10 | 6/6 |
| `fake_split split_pos=midsld` и `fake_disorder split_pos=host+1` на loopback | 0/5 | 0/5 | |

На живом маршруте `multi_disorder` прошёл 17/20 на обоих адресах. Пользователь подтвердил, что в Chrome
видео с ним запускается быстрее, чем с `split_pos=1`. Цифры OpenSSL строже браузера: с `split_pos=1`
мобильный Chrome работал без заметных проблем. Механизм поломки не доказан: вероятно, движок разбирает
только первый сегмент, а SNI у Chrome может оказаться во втором.

## 3. Выводы для архитектуры

1. Пространство параметров описывается декларативно, с ограничениями совместимости и
   канонизацией (эквивалентные конфигурации → один ID).
2. Синтаксис каждого движка рендерится и валидируется по его **реальной** грамматике.
3. Отбор кандидатов — по апостериорным распределениям (Beta-Bernoulli), а не по одному
   наблюдению; решение «стабильно» — по нижней границе доверительного интервала.
4. Контрольный ресурс и baseline-проба отделяют DPI от сбоев сети/DNS/маршрута.
5. Отдельная статистика по каждой цели, IP и семейству адресов; затухание старых данных.

## 4. Сравнение алгоритмов поиска (симулятор)

`adf bench` воспроизводит управляющую логику Fuzzer v2 (тот же список кандидатов, 1 проба со
стопом на первой обязательной цели, топ-5 × 3 повтора, итоговый score) и сравнивает с ADF на
синтетическом цензоре, где известна истинная вероятность успеха каждой стратегии. 8 сидов,
6 целей:

| Алгоритм | Среднее число запросов | Средняя истинная надёжность (худшая цель) | Минимум |
|---|---:|---:|---:|
| Эмуляция Tachyon Fuzzer v2 | 618 | 0.766 | 0.620 |
| ADF, тот же бюджет запросов | 623 | 0.938 | 0.760 |
| ADF, бюджет по умолчанию | 4026 | 0.938 | 0.760 |

Ограничение: модель цензора написана автором ADF и не доказывает превосходства в реальной сети.
Она показывает, что (а) без `fooling`, `multi_*` и маркеров хоста пространство Fuzzer v2 не
содержит лучших для такой модели стратегий и (б) один прогон + 3 повтора дают выбор с
завышенной оценкой. Реальное сравнение выполняется `adf compare` на роутере (Adaptive 2.0,
лучшая стратегия Fuzzer v2, лучшая стратегия ADF — по кругу, в одинаковых условиях).

## 5. Выбор технологий

Контроллер — Python ≥ 3.11 только со стандартной библиотекой (sqlite3, tomllib): поиск и
